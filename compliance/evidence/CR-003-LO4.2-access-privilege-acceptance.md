## 1. Official learning objective

**LO4.2 — Implement fine-grained access control and privilege
management automation.**

Required implementation:

- OPA action rules.
- Just-in-time privilege requests and grants.
- Automatic grant expiry.
- Privilege revocation.
- Privilege audit events.
- Explicit establishment of caller identity and roles in the MVP.

## 2. Identified security gap

The initial implementation accepted caller-declared identities or roles
at selected access-evaluation and JIT endpoints.

Several JIT listing, grant-check and maintenance endpoints also lacked
the required authentication boundary.

OPA policy evaluation alone could not establish whether the identity
and role supplied to it belonged to the actual caller.

These issues were addressed without broadening the PostgreSQL
permissions assigned to ordinary service accounts.

## 3. Implemented remediation

### Verified identity and role mapping

The deployed services verify bearer tokens through the Vault
`auth/token/lookup-self` endpoint.

A valid Vault entity UUID is bound to the application principal as
`vault:<entity_uuid>`.

The demonstrated policy mapping is:

| Vault policy | Effective MVP role |
|---|---|
| `lcnc-access-viewer` | `viewer` |
| `lcnc-access-developer` | `developer` |
| `lcnc-security-reviewer` | `security_admin` |
| `lcnc-senior-security-reviewer` | `security_admin` |

The four live policies were inspected and each granted only `read`
on `auth/token/lookup-self`.

The tests established valid identity claims, denial of unsupported
roles, and consistency between the two service implementations.

### Enforcement boundaries

- JIT request creation validates the authenticated subject and role.
- JIT decisions require a verified authorized reviewer.
- JIT revocations require a verified authorized reviewer.
- Privilege-request and grant listings require reviewer authorization.
- Manual HTTP expiry requires reviewer authorization.
- JIT grant checks require identity matching.
- Governance API forwards the verified caller credential to the
  Governance Automation grant-check endpoint.
- The public access-evaluation route rejects mismatched subjects
  and roles before entering the OPA evaluation path.
- The background expiry worker remains independent of HTTP
  reviewer authentication.

The existing OPA access rules and database schema were retained.

## 8. PostgreSQL RBAC and separation of duties

Live permission inspection confirmed:

- Governance Automation could insert JIT requests, grants and events.
- Governance Automation could not insert or delete applications.
- Governance API could insert applications and access decisions.
- Governance API could not directly delete applications.
- A distinct PostgreSQL administrative role had the privileges
  required for controlled fixture maintenance.

The lifecycle harness initially failed because it attempted
application creation through the Automation database account.

The harness was corrected to use the Governance API for application
registration and a separate administrative connection for controlled,
fixture-specific cleanup.

No application service database privileges were expanded.

Ownership metadata does not itself establish authenticated ownership,
and business-level roles are distinct from database service roles.

## 10. Scope and limitations

This acceptance demonstrates identity-bound access evaluation,
JIT privilege management and OPA decision behavior within the
governance MVP.

It does not establish:

- Universal enforcement of every operation in Appsmith or other
  LCNC platforms.
- Enterprise SSO, MFA or independently certified production IAM.
- A complete organization-wide owner-to-application authorization model.
- Production-hardened Vault, transport security or service identity.
- A dedicated acceptance test of the asynchronous expiry worker;
  the live expiry proof exercised the authorized maintenance route.
- Production authorization coverage outside the tested API paths.

The application-to-application bearer-token forwarding trust boundary
requires appropriate internal transport and deployment protection.

No claim is made that the entire repository test suite passed.

## 11. Final disposition

| Objective | Scoped acceptance |
|---|---|
| LO4.2 — Fine-grained access and privilege automation | VERIFIED |

LO4.2 is accepted within the demonstrated governance MVP scope.

The acceptance establishes real Vault-backed identity verification,

separate learning objectives and are not accepted by this report.
