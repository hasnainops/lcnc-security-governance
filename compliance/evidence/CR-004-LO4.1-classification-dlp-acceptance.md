## 2. Existing implementation

### Automated classification

The project includes the `classification-v1` ML classifier,
automatic classification processing, freshness controls and
classification history.

Prior LO1 assurance work verified the classification workflow,
including advisory inference and classification input freshness.

The ML result provides a suggested classification, confidence
and review-required state.

**ML suggestions do not automatically replace the authoritative
classification stored on the application record.**

No new live ML inference acceptance was performed during this
LO4.1 remediation.

Relevant components:

- `ml-analytics/app/classifier.py`
- `governance-api/app/classification.py`
- `governance-api/app/automatic_classification.py`
- `governance-api/app/classification_inputs.py`

### DLP inspection

The DLP Engine provides inspection for:

- Email-like values.
- SSN-like values.
- Luhn-valid payment-card values.
- Phone-like values.
- Restricted and confidential schema field names.

The engine returns inspection summaries including:

- Engine version.
- Sensitive-data detection flag.
- Finding count.
- Highest detected sensitivity.
- Detected data types.
- Structured findings.

Relevant components:

- `dlp-engine/app/dlp.py`
- `dlp-engine/app/main.py`

### Transfer policy

The Integration Gateway calculates effective sensitivity using
the higher of declared authoritative classification and
DLP-detected sensitivity.

The demonstrated policy blocks:

- Unknown authoritative classification for external transfers.
- Unapproved external destinations.
- Unencrypted HTTP external transfers.
- Restricted data leaving for an external destination.

Confidential data may be allowed to an approved encrypted
destination under the current MVP transfer policy.

## 3. Confirmed security gap

The original Integration Gateway did not validate the consistency
of a successful HTTP DLP inspection response.

Two isolated tests reproduced an unsafe ALLOW decision:

| Malformed inspection evidence | Before remediation |
|---|---|
| Sensitive detection with missing sensitivity | ALLOW |
| Unsupported sensitivity label | ALLOW |

The policy's fallback treatment of unrecognized detected
sensitivity could downgrade defective DLP evidence.

This was a decision-level fail-open vulnerability.

The controlled-egress function can execute an outbound request
after an ALLOW decision, making the result security-relevant.

The tests did not demonstrate actual exfiltration.

## 4. Implemented remediation

The Integration Gateway now validates DLP response consistency
before evaluating transfer policy.

The validation checks:

- Response object structure.
- Engine version.
- Boolean detection flag.
- Nonnegative integer finding count.
- Detected data-type list.
- Presence and structure of findings.
- Individual finding identifiers, sensitivity and counts.
- Agreement between findings and summary metadata.
- Agreement between findings and highest sensitivity.

Malformed, incomplete, contradictory or unparseable responses
produce:

- HTTP 502.
- `decision: block`.
- `reason: dlp_invalid_response`.

Invalid-response failures increment the gateway DLP failure
metric.

The error response does not return raw inspection content.

Only the Integration Gateway implementation and focused
contract tests were changed for this remediation.

No change was made to the ML classification model,
authoritative classification records, OPA access rules
or PostgreSQL service roles.

## 6. Deployment and live DLP acceptance

Only `integration-gateway` was rebuilt and redeployed.

The updated gateway image was verified against the previous
image, and the gateway and DLP Engine were confirmed healthy.

Six real HTTP requests exercised the deployed Gateway and
DLP Engine:

| Scenario | Observed decision | Effective sensitivity |
|---|---|---|
| Clean public data | ALLOW | Public |
| Confidential email detection | ALLOW | Confidential |
| Restricted schema detection | BLOCK | Restricted |
| Unknown authoritative classification | BLOCK | Public fallback in sensitivity field |
| Unapproved external destination | BLOCK | Public |
| Unencrypted external destination | BLOCK | Public |

The unknown-classification case remained blocked despite
the sensitivity display fallback.

Three additional checks against the deployed gateway code
confirmed HTTP 502 BLOCK responses for:

- Missing detected sensitivity.
- Unsupported sensitivity.
- Incomplete inspection evidence.

Those three negative checks mocked DLP responses in-process;
they did not alter the live DLP Engine or issue external
network requests.

## 7. Full Governance API-to-DLP audit acceptance

A uniquely identified application was registered through
the deployed Governance API.

The application had an authoritative classification of
`public`.

The test used synthetic content and the restricted schema
field name `ssn`.

### Verified trust boundary

An attempt to supply caller-controlled `destination_trust`
and `declared_classification` was rejected with HTTP 422.

The Governance API uses the application record as the source
of authoritative classification.

The API also derives destination trust server-side.

### Verified decision chain

The live request followed:

1. Governance API transfer evaluation endpoint.
2. Server-owned application classification and destination trust.
3. Integration Gateway inspection request.
4. Real DLP Engine inspection.
5. Effective sensitivity computation.
6. BLOCK policy decision.
7. PostgreSQL transfer audit persistence.

Observed result:

| Evidence | Value |
|---|---|
| Stored authoritative classification | Public |
| DLP-detected sensitivity | Restricted |
| Effective sensitivity | Restricted |
| Transfer decision | BLOCK |
| Allowed | False |
| Restricted-data external-transfer reason | Present |
| DLP finding metadata | Persisted |
| Raw synthetic marker | Not present |
| Controlled-egress enforcement outcome | NULL |

The evaluation-only endpoint intentionally did not perform
outbound execution.

The NULL enforcement outcome was correct for this endpoint
and must not be misrepresented as proof of controlled-egress
execution.

## 8. Audit data minimization

The `integration_transfer_events` table stores:

- Application identifier.
- Destination scheme, host and trust category.
- Authoritative declared classification.
- Effective sensitivity.
- Decision and reasons.
- DLP detection flag, counts and detected types.
- Gateway and DLP versions.
- Evaluation timestamp.
- Optional execution-enforcement receipt.

The inspected schema does not contain a raw content field.

The isolated acceptance verified that its synthetic raw
content marker was absent from the returned and persisted
audit evidence.

This proves minimization for the tested path; it does not
constitute a universal guarantee about all logging systems.

## 11. Scope and limitations

This acceptance demonstrates the working classification-to-DLP
decision chain within the governance MVP.

The following are not claimed:

- Universal enforcement of all low-code platform operations.
- Guaranteed routing of all Appsmith integrations through the
  protected Governance API boundary.
- A live end-to-end exercise of the controlled-egress outbound
  execution endpoint.
- Production DLP efficacy against all sensitive data formats.
- Enterprise production certification.
- A new live ML inference acceptance during LO4.1.
- A complete organization-wide data-lineage enforcement system.

The direct Integration Gateway API accepts classification and
destination-trust fields. The tested secure integration path
uses the Governance API to derive those fields server-side.

Protection against bypassing that server-owned integration path
is a distinct routing and deployment consideration for LO4.3.

The historical transfer audit rows were not used as substitutes
for the newly executed isolated acceptance.
